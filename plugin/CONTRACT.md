# 契约

这个插件承诺的事很少,而且**明确列出它做不到的**。一个声称能解决冲突、实际只能解决一半的插件,比没有更糟:它会让人以为问题已经处理了。

## 承诺

安装级修复的当前目标与逐版本证据见 [pnpm 插件矩阵](../docs/pnpm-plugin-compatibility.md)。修复器优先识别 alpha 的 app-boot 内嵌加载器，只有精确支持的版本才写入随包补丁并执行 pnpm 重链；它属于本插件的外部 CLI，不是后续 profile 补丁层或网页写入操作。

1. **`dsh-substrate-check` 会在启动前找出所有重复的 entry id**,列出是哪几行在抢,并说明为什么补丁层修不了它。
2. **它不会假称能修。** 遇到补丁层解决不了的冲突,它报告、说明为什么、并列出谁能修,不发出一份照样起不来的补丁。
3. **插件本体在 fiber 状态静默后才报告**,不在 `apply` 里 —— 那时注册表通常还是空的。
4. **它不注册模型可见工具,也不抢占通用名称。** 它只增加命名空间为 `dsh-substrate` 的只读 loopback 状态端点和同名设置卡片槽位,用于把 Host 检测到的事实展示给浏览器。

## 明确不承诺

| 做不到 | 为什么 |
|---|---|
| 修复重复的 entry id | 见下 —— 能修,但不是从这里修 |
| 在启动前报告工具名 / 路由 / 槽位争用 | 那些注册发生在插件挂载期,启动前的静态检查看不到 |
| 从插件里报告 entry id 冲突 | 抛错时**一个插件都没挂上**,没有代码有机会运行 |
| 保证"检查通过 = 一定能启动" | 37% 的路由路径与部分工具名是加载期 config,静态不可判定 |

以上每一条都有实测:[`experiments/lab-duplicate-entry-id.ts`](../experiments/lab-duplicate-entry-id.ts)(14 断言)。

## 重复 entry id:能修,但只能在那一行自己的来源处修

`EntryGroup.update` 在读 `disabled` **之前**就按 id 列表抛错,而 `applyEntryPatches` 复制 override 时**跳过 `id`**。所以停掉一行,它仍占着那个 id;后续补丁层也改不了 id。这是本插件修不了它的全部原因——它是个后来者。

但**拥有那一行的人可以**,三条路都实测过:

| | 做法 | 代价 |
|---|---|---|
| 首选 | 在自己的 `cordis.patch.yml` 里换一个唯一 id | 无。仍可被后续补丁停用与配置 |
| 更好 | 把 id 做成配置项 | 无。部署方自己决定 |
| **下策** | 干脆不写 `id` | `ensureId` 生成随机值,撞车在构造上不可能——但那一行从此**无法按 id 定位**,谁都停不掉、配不了它 |

第三条排在最后是有意的:它靠的是**让那一行变匿名**,而匿名同时意味着谁也够不着它。撞车确实没了,代价是这行退出了所有配置面。**能显式改 id 就不要用它。**

### 为什么"改已存在的 id"这条路根本不存在

不是补丁层不支持,是**每一层都不支持**:

| 试过的地方 | 结果 |
|---|---|
| 后续补丁层 | `applyEntryPatches` 复制 override 时跳过 `id` |
| `EntryTree.update(id, options)` | 签名就是 `Omit<EntryOptions, 'id' \| 'name'>`,类型层面排除 |
| 运行时(`EntryTree.remove` 等) | 够不着 —— 抛错发生在 `mountRootInclude`,那时树还没建起来,**零插件挂载** |

所以能动 id 的只有那一行自己的来源。

对用户侧(既不拥有插件也不改上游的人)**没有干净的解法**——只能拿掉其中一个 bundle,而那会丢掉它的全部功能。

### 更好的提案:从 npm 包名派生 id

不写 id 之所以危险,是因为 `ensureId` 生成的是 `Math.random()` —— 每次启动都不同,谁也定位不到。但 `EntryOptions.name` 已经是模块说明符,对插件行来说**就是 npm 包名**,而 npm 保证包名唯一。从它派生,就同时拿到了两样:

```
@anweat/dsh-browser            -> anweat-dsh-browser
@deepseek-ai/dsh-builtin-browser -> deepseek-ai-dsh-builtin-browser
```

不同包不可能撞车(npm 的唯一性直接传递),**而且 id 是确定的,所以仍然可定位**。原型实测(13 断言):两次启动 id 完全一致;同一个包装两次时带序号;写了显式 id 的行为完全不变,是纯增量。

**但有两个约束是跑出来才知道的:**

1. **派生不能放在 `ensureId` 里。** `EntryGroup.update` 先循环给每行 `ensureId`,那时 store 还是空的——同一个包的两行会双双拿到同一个 base 然后当场撞车。只有批次循环看得见兄弟行。
2. **派生必须早于 `applyEntryPatches`。** 补丁跑在组合期,加载期才派生的话,补丁运行时那一行**还没有 id**,于是"可定位"这个卖点不成立。改动要落在组合出行列表的那一刻,让补丁和 loader 对同一个名字达成一致。

第二条是这个提案能不能成立的关键,也是它比"让 id 可配置"更值得提的原因:**它不需要任何插件作者做任何事。**

### 完全自动、零作者改动:可以,但不能是插件

派生只对"没写 id"的行生效,而真实的冲突两边通常都写死了 id。要覆盖那种情况,得在**补丁读到行列表之前**改写后来者的 id —— `Include.prototype.applyPatches` 收的正是那份列表。实测(11 断言):

```
基线                两个包都写死 id: browser        启动失败
自动去重            后来者改为包名派生的 id          启动成功,两个插件都挂上
按原 id 定位        命中第一个认领者                 ✓
按派生 id 定位      命中后来者                       ✓ 补丁看得见它
同一个包装两次      照样抛错                         ✓ 真错误不被藏起来
id 本来就唯一       零改写                           ✓
```

**两个插件作者都不用改任何东西。**

最后两行是这个设计比"加 `-2` 后缀"好的地方。派生是包名的函数,所以两行派生出同一个 id **当且仅当它们是同一个包**——那是配置错误,不是共存问题,于是规则直接不改写它,让它照常响亮地失败。后缀方案会把这类错误一并静音。

**但它仍然不能是插件。** 改写必须发生在 `mountRootInclude` 之前,而插件是被那一步挂载的。能装它的形态是 Node 预加载,或者上游把这条规则收进 loader —— 后者才是正解。

### 换掉内核那段检查:能,但本插件不会这么做

那个检查在一个导出的类方法里(`EntryGroup.prototype.update`),替换它约 12 行,可逆,实测有效:两个同 id 的行都挂了起来,第二个被自动改名成 `browser-2`。用 Node 预加载就能装,不用 fork:

```bash
node --import tsx/esm --import ./dedup-preload.mjs <app>
```

**但本插件不提供它,也不建议长期用。** 三条代价都是真的:

1. 它改的是 vendored 内部实现,**上游一升级就静默失效**
2. 自动改名后,任何按 id 定位第二行的东西都会落到第一行上——**包括按插件文档里那个 id 写的补丁**
3. 它对**所有** id 生效,于是"同一个 bundle 被装了两次"这种真配置错误,从响亮变成安静

第三条最要命。那个检查存在是有理由的,静默改名会把一类错误藏起来。

作为**临时逃生口**它成立;作为插件要发布的东西不成立。实测在 [`lab-id-injection.ts`](../experiments/lab-id-injection.ts)(6 断言)。

## 工具名冲突:不改名,分层

工具名和 entry id 是两类问题。`browser_click` 被四个真包注册,而它们做的是同一件事——这时你要的是一个能用的,不是四个让模型挑。

真实数据(5 个已发布的 browser 插件,53 个不同工具名,11 个撞名):

| | agent 看到的工具 |
|---|---|
| **scope 分层** | **53 个** —— 撞名的各留一个赢家,42 个独有的全保留 |
| 加前缀 | 72 个 —— 多出 19 个近义工具 |

分层保住的正是最该保的:`dsh-builtin-browser` 的 33 个工具里 25 个独有(human takeover、`browser_execute`、`browser_a11y`、CAPTCHA hand-off),一个不丢。语料上同样的结论——**553 起工具名争用全部解为分层,没有一个需要改模型可见的名字。**

前缀合适的场合是"同名但做的事不同"。`browser_click` 不是那种。

### 决定在注册那一刻做,所以不需要目录

早先的做法是先裁决出谁会输、再把他们放进 scope,那需要一份"哪个包注册哪些工具"的目录——而目录必然多报、每次 DSH 发版就过期,是整套东西里唯一无法做准的一环。

但工具冲突发生在 `register` 被调用的那一刻,而垫片正坐在那个调用上。那一刻"这个名字被占了吗"有确切答案,直接问注册表就行:

```
名字空着   照常进全局命名空间,行为与没装垫片时一致
名字被占   进这个插件自己的 scope,不抛错
赢家       先注册的那个,由行序决定
落败者     工具没被删,经它的 scope 仍可取到;它的其它工具照常全局可见
run_code   照样抛错 —— 自适应不给保留名开后门
```

10 条断言打在真 `ToolRuntime` 上([`lab-adaptive-shim.ts`](../experiments/lab-adaptive-shim.ts))。**目录这一环整个不需要了。**

## 修复怎么装:一笔安装级事务,不是设置开关

`patchedDependencies` 改的是 DSH 安装工作区里的 loader,不是插件自己的运行时设置。它有四个彼此独立的事实:

```
准备声明 → pnpm 重新链接依赖 → 重启 DSH → 新进程验证
```

少任何一步都不能写成“已修复”。尤其“文件已写入”和“当前进程已加载”不是一回事:在 DSH 仍运行时完成 `pnpm install`,磁盘上的 loader 已经变化,内存里的旧模块仍会继续运行到重启。

因此浏览器卡片现在是**只读引导面**:它显示精确状态和一条可复制命令,不从正在运行的 DSH 里重装 DSH。真正的写入、`pnpm install` 与磁盘验证由外部命令完成:

```bash
dsh-substrate repair --apply
dsh-substrate repair --revert
```

命令会重新定位目标、校验 loader 的精确版本、展示将操作的工作区并要求确认;版本或路径不匹配时,在写任何文件之前拒绝。

### 写到哪里,是这件事唯一的难点

第一版按钮写进 profile,成功、无警告、无报错、**毫无效果**。profile 不依赖 loader —— `healProfilesModuleFallback` 在 `$DSH_HOME/profiles/node_modules/` 下为 dsh 依赖闭包里的每个包建一条符号链接,指向它在 dsh 安装目录里的真实位置,Node 从任何 profile 往上找都会找到那里。所以 profile 跑的 loader 从来不是 profile 自己的。

`patch-target.mjs` 顺着那条链接走到真实目录,再往上找到最外层 `node_modules` 的父目录 —— 那才是 pnpm 会读的工作区。对安装位置先分三类:

```
installed    找到了真实安装工作区          → 继续校验版本与事务状态
source       loader 在源码 checkout 里     → 拒绝 patchedDependencies
unresolved   找不到那条链接                → 拒绝写,并把找过的位置说出来
```

`source` 这一条是第二个坑,比第一个更隐蔽:**pnpm 不给工作区内的包打补丁**。从源码跑的 dsh(比如开发用的克隆)解析到的 loader 是 `vendor/include`,往那儿写一份声明,pnpm 照样接受、照样忽略 —— 和第一个 bug 一模一样,只是换了条路径。两种情况都没有任何可观察的区别,所以分类器按情况逐个钉死,而不是只测一条通路。

安装目标确定后再分事务状态:`available`、`install-required`、`restart-required`、`verified`,以及撤销方向对应的两个等待态。追加而不是重写清单,是因为那个文件是共用的:DSH 管着 `nodeLinker`、`autoInstallPeers`、`strictDepBuilds`,用户也可能加了自己的键。重写会把两边都悄悄抹掉。撤销把清单还原到写入前的字节。

## 设置里那一项:静默窗口

卡片渲染出来的前提,是 Host 侧注册了同名的设置命名空间——插件设置页发布的是"Host 服务的命名空间"与"注册进 `settings.plugin.item` 的卡片"的**交集**,键对不上的卡片会被无声丢弃。

`settleMs` 是这个命名空间的内容:启动报告在 fiber 状态安静多久之后出。机器越慢、profile 越大,需要的窗口越长;太短就会报告一棵没搭完的树。修复区不走设置文档,`/dsh-substrate` 也只向浏览器提供状态;安装动作只存在于外部 CLI。

### 为什么不能装上就自动生效

**pnpm 不读依赖包声明的 `patchedDependencies`。** 实测,同一份补丁文件:

```
依赖的 package.json          未应用
根 package.json              未应用(pnpm 11 已废弃该位置)
pnpm-workspace.yaml          已应用 ✓
```

所以采用补丁必然是安装工作区的一次明确动作。这不是要绕开的限制,而是这件事可信的原因。CLI 缩短步骤,但不取消版本检查、改动展示和用户确认。

## 三个入口,因为诊断和修复发生在不同时刻

```
启动前   dsh-substrate-check <composed.yml>    重复 entry id —— 插件不可能报的那类
进程外   dsh-substrate repair --apply          写声明、重链依赖、验证磁盘
启动后   插件卡片与日志                        验证新进程真正加载了什么
```

中间那道线不是设计取舍,是运行时的事实:重复 id 在任何 `apply` 之前就被拒绝了。

## 版本

运行时历史基线为 `dsh-v0.1.1-rc.2-5-g50854a854f`;分发补丁精确接受 loader `1.0.6`、`1.0.7`,由真实安装目标的版本选择,未知版本继续拒绝。两个 npm 发布包的运行时代码相同,均已通过真实 pnpm 应用/新进程行为/撤销验证。DSH alpha 的逐标签覆盖范围见 [适配记录](../docs/alpha-compatibility.md),不承诺未来 alpha 自动兼容。

alpha Connection 将 Host/Origin 校验和浏览器会话认证统一应用到通道;旧版的第三参数 `authority: 'loopback'` 在 alpha 不再是独立边界。卡片状态继承 DSH 的已认证访问范围,始终没有安装写入 RPC。浏览器操作复用官方 Connection,不自建 cookie 或 RPC 信封。

**这个插件的目标是变得不必要。** 上游只要让 entry id 可配置(或让 `disabled` 的行退出 id 检查),`check` 的主要用途就消失了;上游给客户端行加 rank、给令牌加导出面,这里对应的部分同样该删掉。衡量它的标准是**还剩多少**,不是还能做多少。详见 [ADAPTATION.md](../ADAPTATION.md)。
