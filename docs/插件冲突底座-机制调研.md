## 一句话结论

DSH 有 **host 平面**和 **agent 平面**两层,模型可见的东西本该活在 agent 平面(预设)里;而生态里 9,873 个插件**全部**插在根上、注册到全局层——站错了平面。553 起工具名冲突不是生态不守规矩,是**几乎没人知道有两个平面**。底座要做的不是发明机制,是**把插件搬到正确的平面**,并补上 DSH 缺的两样东西:**注册收集期**和**显式顺序声明**。

### 更大的模式:大家都在自带基础设施

`entry-id` 撞名 Top 榜(共 452 组):

> **推论:底座有两个同等重要的职责。** 一是冲突裁决,二是**做共享基础层**——提供一次 `storage` / `code-runtime` / `agent-presets`,让插件停止各带一份。

### 第 10 类:HTTP 路由(已补测)

**机制**(`packages/host/webserver/src/index.ts:110`):`register` 对重复路径**直接 throw**;`registerUpgrade`(WebSocket)与 `fallback`(单座位)同样。**完全没有 scope 分层**,就是个扁平 `Map<path, route>`。所以这类只能靠 isolate + 代理,没有第二条路。

**实测**(抽样 503 个已知注册路由的仓库,197 个因并发限流失败):

```
路由注册点 1,739 | 字面量 1,087 (63%) | 非字面量 652 (37%,静态不可判定)
不同路径 847 | 被 2 个以上包争用 49 (5.8%)
```

最挤的路径:`/sidebar/*` 各 6 个包、`/dsh-market/*` 各 4 个包、`/plugins` 5 个包。

**但要如实说明:这批争用主要是分叉,不是独立撞车。** `/sidebar/*` 和 `/dsh-market/*` 是整套路由面被多个包共享——典型的同一插件分叉。`/plugins`(官方 `client/modules` 注册的前缀)那 5 个里,一个是 dsh 仓库自身(`@deepseek-ai/dsh-root`),其余是桌面端/GUI 套壳,它们替换整个宿主而非与之共存。

**结论**:路由冲突作为**机制**是真实且严重的(硬抛、无 scope 兜底),但**生态实测证据质量低于工具名**——37% 静态不可判定,且头部争用是分叉聚簇。不宜作为底座的首要卖点,但必须在设计中覆盖。

## 第二部分 · 机制地图(已验证)

### 2.1 两个平面

出厂架构:**根/host 平面**持有注册表、沙箱与审批栈、持久化、模型路由;**预设/agent 平面**持有一切模型可见的东西。

证据一 —— `apps/cli/config/agent-presets/standard/agent.cordis.yml` 开头:

> 这个文件是 AGENT-PLANE 组合。roster 把它挂载**一次**在常驻 scope 下,每个 session 命名它即通过 scope 父子关系加入……主机组合保留预设**不该拥有**的一切:注册表本身、沙箱与审批栈、持久化、模型路由。

证据二 —— `packages/preset/agent-presets/src/index.ts` 的 `agent/created` 告警:未加入预设的 agent,"其工具、提示段、技能目录都解析自**空的全局层**"。

证据三(定量)—— **web-app 在根上禁用的 24 行,22 行在 standard 预设里重新挂上**。例外只有 `hmr` 和 `tool-str-replace-editor`,是真关。

> 结论:全局层**设计上应该是空的**。生态全挤在这一层。

### 2.2 scope 分层与链序

`ToolRuntime` 结构:

```
ToolRuntime (Service)
 └ ScopedLayers<ToolLayer>
     ├ 全局层(eager)
     └ 每个 scope 一层(lazy)
ToolLayer = { tools: NamedEntries, restrictions, guards, mode }
```

- `register()` 走 `layers.effect(this.ctx, ...)`,**层由调用方的 scope 决定**(`packages/core/tools/src/index.ts:1037`)
- `view(scope)` 沿 scope 链由远及近合并,**近的遮蔽远的**;restrict 沿链取交集(`:1152`)
- 重名错误来自 `ToolLayer` 构造时传入的错误工厂(`:714`)

**加入方式**:`bindScopeParent(agentKey, standingKey)` 把 agent scope 认预设的常驻 scope 为父。

### 2.3 isolate realm

`vendor/loader/src/config/isolate.ts`:

```ts
interface EntryOptions {
  intercept?: Dict | null
  isolate?: Dict<true | string> | null    // 一等 entry 选项,配置层可声明
}
```

- `isolate: { x: true }` → LocalRealm,符号 `x#<entryId>`
- `isolate: { x: 'label' }` → GlobalRealm,符号 `x@label`

`PatchOptions` 本就带 `isolate`,所以**补丁层可以给任意行加 realm,不需要改 dsh 上游**。

**易错点**(预设文件原话):共享标签**不会**汇集实例——`provide()` 在同一 realm 符号下第二次注册就抛错;**标签连接的是 REALM,不是实例池**。实测复现:第二个 shim 挂进同一 realm 报 `service "tools" has been registered`。

正确模式:`cordis:group` + `isolate: { x: true }`,standard 预设用了三次(planning / compaction / delegation)。

### 2.4 三个挂钩点

| 挂钩点 | 时机 | 能力 | 谁能用 |
|---|---|---|---|
| `setup(agentCtx)` | 铸出 agentCtx 后、**发布前** | 组合整个 scoped world;抛错**全回滚**,两个 id 都不发布 | **只有 agent 创建方能传** |
| `AgentSetupCommit.commit()` | 发布边界,**同步** | 注册都进来了、还没发布 —— **冲突预检的正确位置** | 同上 |
| `agent/created` 同步监听器 | 发布时 | 抛错**否决发布** | **任何插件都能挂** |

契约原文(`packages/core/agent/src/index.ts:116`):

> 工厂在铸出 `agentCtx` 后 await setup,但在插入或宣告 session 与 agent **之前**……通过 `agentCtx` 注册的一切都存在于 `session/created`、`agent/created`、`agent/session-start` 和首次提示装配之前。setup 抛错/拒绝、commit 抛错或属主释放会回滚 scope,两个 id 都不发布。

**关键限制**:`setup` 是 `CreateAgentOptions` 的字段,由**创建方**传入。插件**可以**单方面否决,**不能**单方面组合。

### 2.5 前端平面:有 priority,无配置缝

**槽位模型**(`packages/client/ui-slots/src/index.ts:787`):

- `priority` 升序,默认 0,**最低者渲染**
- 同一格 + 同一 priority → **抛错**;不同 priority → 遮蔽
- `registrant` 字段由**运行时自动打上**("the runtime Service wrapper stamps the caller's fiber name")——底座无需插件配合即可归属每个注册
- `abdicated`:崩溃的条目自动退位,官方 UI 回来(动态包的崩溃监理缝)

**但客户端没有配置层。** 客户端用同一个 `Loader` 类(isolate 插件挂着),但创建 entry 的方式是:

```js
const rows = this.manifest.plugins.map(row => row.id)
const id = await loader.create({ name })     // 只有 name,没有 group / isolate / config
```

`BootPluginRow` 只有 `{ id, inject, immediately }`。**所以底座无法在前端做隔离、分组或改 priority。**

**唯一的杠杆是二元取舍,但它是真实的**(`packages/client/modules/src/index.ts:483`):

```js
for (const entry of this.ctx.loader.entries()) {
  if (entry.options.name === entryName && entry.fiber !== undefined && !entry.disabled) { qualifies = true; break }
}
if (!qualifies) return this.table.delete(entryName)
```

一个包的前端半**只有在它的主机 entry 活着且未禁用时**才进启动清单。所以主机侧 `disabled: true` → 前端半消失 → 它的槽位注册不会发生。

> **推论**:前端冲突(single 槽 24 组 / keyed 62 组)底座只能**选一个、禁掉其余**——粗粒度但确定,总好过抛错。要做到分层遮蔽,必须让 `BootPluginRow` 携带 priority,那是上游改动。

### 2.6 事件平面:顺序不可声明,且可被静默截断

**派发语义**(`docs/cordis-primer.md`):

| 模式 | 顺序 | 有返回值 |
|---|---|---|
| `waterfall` | **注册顺序** | 有 |
| `serial` | **注册顺序** | 有 |
| `parallel` | 并行 | 无 |

`ctx.waterfall` 是环绕式中间件:监听器收到 `(...args, next)`,调 `next()` 向下委托,**不调就短路**。

**顺序控制只有 `prepend?: boolean`**(`vendor/cordis/src/events.ts:112`)——二元前置,没有数值优先级。而且 **DSH 自己没有任何一处**用它做事件顺序控制。

所以:**顺序 = 注册顺序 = 激活顺序 = `inject` 依赖解析的产物,配置层不可声明。**

任何监听器都能不调 `next()` 静默截断整条链。`tools/pre-execute` 上有 **349 个包**在监听,其中任何一个早注册并短路,下游全部失效。

注:README 里的 "reorderable pre-execute waterfall" 指的是监听器**自己**可以短路/改写,不是存在优先级系统。

#### 但底座仍有三个抓手(实验 4 验证,5/5)

**曾判断为"基本不可治",这个判断是错的。** 无需任何上游改动即可做到:

**① `prepend: true` 稳拿头位**,即使比对方晚注册:

```
trace: ["substrate","ordinary-1","ordinary-2"]
```

且全生态 + DSH 自身**没有任何一处**在用 `prepend`,所以这个头位事实上由底座独占。

**② 哨兵对能检测短路** —— 前哨兵(prepend)开场置位,尾哨兵(最后注册)复位;尾哨兵没跑 = 有人截断了链:

```
未短路: ["front","plugin-a","plugin-b","plugin-c","rear"]   尾哨兵到达
被短路: ["front","plugin-a","plugin-b(SHORT)"]              尾哨兵缺席 → 检出
```

**③ `ctx.tools.guard()` 免疫短路** —— 流氓监听器返回 blanket `allow` 短路了整条 waterfall,**guard 仍然执行且其拒绝压过 allow**。所以**底座自己在工具管线上的策略是顺序无关、不可被截断的**。

**仍然做不到的**:控制第三方之间的顺序;定位**具体是哪个**监听器短路的(但底座控制第三方的挂载,可在**安装期**逐个挂载 + 探针二分定位,不必每次启动都做)。

> 修正后的定位:事件平面**不是不可治,而是"可检测 + 自身策略可保证,但不可编排"**。真正需要上游的只剩"第三方之间的顺序编排"。

### 2.7 热重载通道

`vendor/hmr/src/index.ts:504`:重载在**同一个父上下文**下新建 fiber、沿用同一份 config、转移 entry 绑定,再释放旧的;发 `hmr/reload(Map<Plugin, Reload>)`。

推论:
- 插件在底座 realm/scope 里重载后**仍在其中**
- 但注册被拆掉重做 → **冲突裁决必须幂等,且能在重载时重新施加**
- 出厂两个 profile 都 `hmr: disabled: true`;38 个生态插件也关它

### 2.6 DSH 相对 MC 缺的两样

| MC | DSH 现状 |
|---|---|
| mod 序号定加载顺序,可显式改 | **配置层无顺序语义**。base bundle 注释:"Row order carries no load semantics (activation is service-availability driven)" |
| 统一注册器**事先**查冲突 | **无收集期**。注册即时生效,冲突在第二个注册者身上抛 |

但 **scope 链序补上了第一样**:实测确认优先级 = 声明的链序,不是激活顺序。

### 实验 3:`lab-loader-isolate.ts` —— 6/6(**真 loader,端到端**)

前两个实验验的是 Cordis 原语(`ctx.extend` 直接改 isolate 映射)。这个验的是底座真正依赖的东西:**loader 的 `isolate` entry 选项**能否在消费者和真服务之间插进一个 shim。

配置(全部声明式,零代码):

```yaml
- id: real
  name: ./real.mjs          # 在根上 provide `demo`

- id: sandbox
  name: cordis:group
  group: true
  isolate:
    demo: pluginrealm        # ← 全部机关在这一行
  config:
    - id: shim               # 在 realm 内 provide `demo`,经 ctx.root 转发
      name: ./shim.mjs
    - id: plugin-a           # inject: ['demo'] → 解析到 shim
      name: ./consumer.mjs
      config: { owner: pkg_a }
    - id: plugin-b
      name: ./consumer.mjs
      config: { owner: pkg_b }

- id: outsider               # 组外,应解析到根服务
  name: ./consumer.mjs
```

结果:

```
outsider  → resolved: real                        (组外,拿到根服务)
pkg_a     → resolved: shim, realWho: real, got: "bash"
pkg_b     → resolved: shim, realWho: real, got: "pkg_b__bash"

root registry: [{name:"bash", owner:"pkg_a"}, {name:"pkg_b__bash", owner:"pkg_b"}]
```

**结论:底座的拦截层可以纯配置声明,不需要改 dsh 上游。**

### 由此推出:怎么把第三方插件弄进 sandbox 组

它们全插在根上,而 `applyEntryPatches` **没有"移动"操作**——只有 insert / override / disable。但组合可用:

1. `- id: <他们的行 id>` + `disabled: true` —— 在根上禁掉
2. `- insert:` 带 `id: sandbox` —— 重新插进底座的组

前提是**知道他们的 entry id**,而这正是生态分析管线的产出(9,216 个根插入行、entry id 已全部提取)。底座可以随包发一份生成的清单。

复现:

```bash
cd /d/codeproject/dsh-lab
node --import tsx/esm lab-isolate-proxy.ts     # 10/10 Cordis 原语
node --import tsx/esm lab-real-registry.ts     # 12/12 真 ToolRuntime + 链序
node --import tsx/esm lab-loader-isolate.ts    #  6/6  真 loader,端到端
```

**踩到的两个坑**:`createScope` 造的裸上下文读不到服务(Cordis inject 纪律,必须由声明 `inject` 的真插件注册);`createScope(ctx, key, {parent})` 自己会绑父,再调 `bindScopeParent` 会被拒。

## 第四部分 · 底座设计选项

### 主机制:scope 分层(A 方案)

每个第三方插件一个 scope,按**声明顺序**挂到 agent 的 scope 链上。

- **不改名** —— `bash` 还叫 `bash`,只是"哪个实现对这个 agent 可见"由链序决定
- 冲突从"崩溃"变成"确定性裁决"
- 直接复用 `view()` 已有的遮蔽语义

### 兜底机制:isolate + 代理(B 方案)

给没有 scope 模型的服务用,尤其 **2,702 个包注册的 HTTP 路由**——那类只有 B 能覆盖。

### 底座的形态(已修正)

**曾考虑但已否决:包装 `agentPresets` 服务。** 技术上可行(消费面 11 个方法,主机侧只有 api-proxy 10 处 + subagent 1 处),但**被 scope 链的形状否决**:

> `dsh-scope` 契约:绑定是**一次性**的,已有父的 key 再绑会抛;`scopeChainOf` 返回 `[key, parent, …]`。

scope 链是**一条线,不是树**,而 `mount()` 已经把 agentKey 绑到预设的常驻 key 上。**底座无法给已加入预设的 agent 再插一个祖先**——第三方插件要对 agent 可见,就必须本来就在那条线上。

**因此:底座应当是预设的宿主,而不是预设的包装器。**

| 形态 | 依赖 | 能力 |
|---|---|---|
| **守门员** | 无(纯插件,挂 `agent/created` 抛错否决发布) | 预检 + 拒绝,给出"这套插件装一起会炸" |
| **预设宿主** | 补丁层(实验 3 已验证可行) | 提供预设根、裁决 `default` 归谁、把第三方插件按裁决顺序编排进预设组合 |
| **共享基础层** | 补丁层 | 提供一次 `storage` / `code-runtime` 等,消解 452 组 entry-id 撞名的头部 |

**建议路径**:守门员先行(零依赖、立刻可用),预设宿主为主体,共享基础层随后。那 28 个抢 `default` 的包正是预设宿主要接管的第一件事。

### 还需要底座自建的

- **注册收集期**(`DeferredRegister` 等价物):先收集 → 查冲突 → 再应用
- **顺序声明**:配置层的插件优先级,映射到 scope 链序
- **裁决策略**:先到先得 / 用户显式选 / 按 agent 分层让两个都保留

## 第五部分 · 未解问题

1. **agent 平面迁移是否需要创建方配合。** 已查清:共 8 条创建路径(ACP、headless、api-proxy ×3、SDK server、subagent ×2、resume)。
   - **Web 路径有唯一瓶颈**:`composeAgent()` 内部走 `ctx.get('agentPresets')` —— 一个**服务查找**,而实验 3 证明服务查找可被 `isolate` 拦截。`api-gateway` 和 `agent-presets` 都是独立可打补丁的行,所以底座**可以**包装 `agentPresets` 而不改上游。**待验**:该服务接口更复杂(`list`/`resolve`/`mount`/`composeFrom`/`recompose`),包装是否完整无损。
   - **headless 明确不用预设**(源码注释:"这个 bundle 不组合预设 roster,模型可见的行留在 host 平面,agent 从全局层读取")。所以冲突性质**按 profile 分裂**:headless 下全局层是正确归宿;web 下全局层本该为空。生态里 4,843 个包声明前端半 → 绝大多数瞄准 Web,即平面错配真实存在的那一侧。
2. ~~前端半没有 scope 模型~~ **已查清(见 2.5)**:客户端无配置层,底座只有"二元取舍"一个杠杆。要做分层遮蔽必须让 `BootPluginRow` 携带 priority——**这是上游改动**。
3. ~~`webServer` 路径撞车未统计~~ **已补测(见第一部分)**:机制严重(硬抛、零 scope),但生态实测证据质量低于工具名(37% 不可判定 + 头部是分叉聚簇)。
4. ~~事件顺序不可见不可控~~ **已查清(见 2.6)**:顺序 = 注册顺序,只有二元 `prepend`,DSH 自己都不用。**且监听器可静默截断整条链**——底座最难覆盖的一类。
5. **`entry-id` 撞名(452 起)** 没有现成原语,需要挂载时按包名重写 id。头部全是基础设施行(`storage` 29 / `agent-presets` 26 / `code-runtime` 25)。

### 按可治理程度排序(底座的现实边界)

| 平面 | 底座能做什么 | 依赖 |
|---|---|---|
| **工具名** | 完全可治:scope 分层 + 链序裁决,不改名 | 纯配置 |
| **entry id / 配置行** | 完全可治:禁旧行 + 组内重插 + 按包名重写 id | 纯配置 |
| **HTTP 路由** | 可治:isolate + 代理改写路径 | 纯配置 |
| **前端槽位** | **仅能二元取舍**(选一个、禁其余) | 纯配置;分层遮蔽需上游 |
| **事件平面** | **可检测短路 + 自身策略免疫短路**;不可编排第三方顺序 | 纯配置;编排需上游 |

## 第六部分 · 开发取舍清单

开工时逐条决策,每条给推荐。

### 6.1 裁决策略:同一目标多个争用者,谁赢

| 选项 | 说明 | 适用 |
|---|---|---|
| 先到先得 | 按补丁层序,第一个保留原名/原位 | ❌ 不推荐:层序本身不稳定,用户无法预期 |
| **声明顺序** | 底座配置里显式列出插件优先级,映射到 scope 链序 | ✅ **推荐**。对应 MC 的 mod 序号,可显式改 |
| 用户交互选择 | 冲突时弹窗让用户选 | 作为声明顺序缺失时的兜底 |
| 全部保留 + 命名空间 | 冲突方加前缀 | ❌ 工具名不适用(改了模型可见的 API);entry id 适用 |

### 6.2 工具名冲突:分层还是改名

- **分层(scope)**:`bash` 仍叫 `bash`,不同 agent 看到不同实现。**推荐**——不动模型可见的 API
- **改名**:`pkg_b__bash`。仅在必须让两个实现**同时对同一 agent 可见**时使用

### 6.3 底座自身的挂载位置

必须在**它要管的插件之前**激活。但激活顺序由 `inject` 驱动、配置不可声明——所以底座**不能依赖顺序**,只能依赖:插件被它重新编排(禁旧行 + 组内重插),此时插件的挂载点由底座的配置决定。

### 6.4 失败姿态

| 情形 | 选项 | 推荐 |
|---|---|---|
| 检出 critical 冲突 | 拒绝启动 / 禁用冲突方 / 仅警告 | **可配置**,默认"禁用冲突方并显著提示" |
| 底座自身失败 | 整体不启动 / 退化为直通 | **退化为直通**——底座不该成为新的单点故障 |
| 热重载后 | 重新裁决 / 沿用旧决定 | **重新裁决且幂等**(见 2.7) |

### 6.5 生态清单从哪来

- **随包发布静态清单**:确定、离线可用,但会过时
- **运行时扫描已装插件**:实时,但要读 `ctx.loader.entries()` + 解析各包 manifest
- ✅ **推荐两者兼有**:静态清单做已知冲突库,运行时扫描兜底未知包

## 第七部分 · 建议的上游改动(PR 清单)

只列**配置层治不了**、且改动面小的。按价值排序。

### PR 1 · 事件监听数值优先级 —— 最高价值

**问题**:1,951 个包干预回合/工具管线,顺序 = 注册顺序,只有二元 `prepend`,且监听器可静默截断整条链。

**改动**:`EventOptions` 增加 `priority?: number`,派发前按 priority 稳定排序。`vendor/cordis/src/events.ts` 的 `register()` 已经在做 `unshift`/`push` 二选一,改成有序插入即可。

**注意**:这是**vendored Cordis**,按 `vendor/README.md` 的同步流程走并登记为 local modification;或推到 Cordis 上游。

### PR 2 · 短路可观测 —— 次高价值,改动最小

**问题**:waterfall 监听器不调 `next()` 就静默截断,没有任何信号。

**改动**:短路时发一个诊断事件(谁短路了哪个事件),或在 dev 模式下记录。**不改变语义,只加可观测性。**

### PR 3 · `BootPluginRow` 携带 priority

**问题**:客户端槽位有 priority 但没有配置缝,底座只能二元取舍。

**改动**:`BootPluginRow` 从 `{ id, inject, immediately }` 扩展出 `priority?: number`,由主机侧清单生成时写入,客户端 `loader.create()` 透传。改动集中在 `packages/client/modules`。

### PR 4 · `agent-presets` 的 `default` 归属仲裁

**问题**:28 个包各自设 `default`,用户静默拿到别人的默认预设。

**改动**:检出多层设置 `default` 时告警并给出层来源;或提供显式的"用户选择优先"语义。

### 不建议提的

- **全局 setup 贡献点**:我们已确定底座应做预设宿主,不需要它
- **工具名命名空间**:分层已经够用,且改名会动模型可见 API

## 第八部分 · 通用结构层(适配层设计)

目标:**dsh 更新时只改最外一层**。三层划分,依赖方向单向向下。

```
┌─ L3 应用适配层(易变,跟着 dsh 走)
│    把决策翻译成 dsh 产物:补丁行 / isolate realm / 预设组合 / disabled 标记
│    每个 dsh 机制一个适配器,机制变了只换适配器
├─ L2 裁决层(稳定,纯函数)
│    (contributions[], policy) => decisions[]
│    无 dsh 依赖,可单测,可离线跑
└─ L1 贡献模型(最稳定,词汇表)
     { plane, kind, target, owner, priority, source }
```

### L1 · 贡献模型

我的分析管线已经在用这套词汇,它对 dsh 的耦合只在 `kind` 的取值上:

```
plane   host | client
kind    tool | slot | route | event | entry-id | config-row | service
target  名字/路径/id
owner   包名(前端由 registrant 自动提供,主机由调用方 ctx 推断)
priority 声明顺序(底座配置给出)
source  file:line
```

### L2 · 裁决层

纯函数,输入贡献列表 + 策略,输出决策:

```
decision = { target, winner, losers[], remedy }
remedy  = layer(scope 分层) | rename | disable | isolate | report-only
```

**不接触 dsh 任何 API**。这一层承载 6.1–6.4 的全部策略,可以离线在生态数据上回归测试——我那 9,873 个插件的数据集正好是它的测试语料。

### L3 · 适配层(每个机制一个)

| 适配器 | 输出 | 依赖的 dsh 机制 | 脆弱度 |
|---|---|---|---|
| `patch-emitter` | `cordis.patch.yml` 行 | `applyEntryPatches` 语义 | 低(已稳定) |
| `realm-emitter` | `cordis:group` + `isolate` | loader isolate 选项 | 低(实验 3 已验证) |
| `preset-emitter` | `agent.cordis.yml` | 预设组合格式 | 中 |
| `scope-binder` | scope 链序 | `dsh-scope` API | 中 |
| `client-gate` | 主机行 disabled 标记 | 清单派生规则(2.5) | 中 |

### 版本适配:能力探测而非版本号判断

底座启动时**探测**可用机制,而不是判断 dsh 版本号:

```
isolate 可用?        试探一个 realm 是否生效
BootPluginRow.priority 可用?  读清单类型/试写
EventOptions.priority 可用?   读 EventOptions 形状
```

探测结果决定 L3 启用哪些适配器,缺失的降级到 `report-only`。这样 **dsh 加了 PR 1–3 之后底座自动升级,没加也不崩**——对应 Forge 的版本门控兼容。

## 第九部分 · 测试计划

分层与第八部分一致:**越靠下越稳定、越该先写、越该多测**。

### T1 · 裁决层(L2)—— 离线,零 dsh 依赖,先写

纯函数 `(contributions[], policy) => decisions[]`,不碰任何 dsh API。

| 测试 | 语料 | 断言 |
|---|---|---|
| 单元:每种 remedy | 手写最小用例 | layer / rename / disable / isolate / report-only 各自的触发条件与输出 |
| 单元:裁决策略 | 手写 | 声明顺序生效;缺声明时回退策略确定;同优先级冲突有明确处理 |
| 单元:幂等 | 手写 | 同一输入跑两次决策完全相同(热重载要求,见 2.7) |
| **回归:全生态** | **9,873 个真插件的贡献数据** | 无异常;决策覆盖 553+452+89+77+28 起已知冲突;**产出"裁决后有多少插件能共存"这个数** |
| 边界 | 构造 | 空输入 / 单方 / 100 方争同一目标 / 环形依赖声明 |

> 这一层可以**现在就写**,不等任何机制确定。它的回归语料已经在手。

### T2 · 适配层(L3)—— 对 `dsh-lab` 跑

每个适配器一套,都要有"产出物正确"和"产出物真能生效"两级。

| 适配器 | 产出物正确 | 真能生效 |
|---|---|---|
| `patch-emitter` | 生成的 patch 行结构符合 `PatchOptions` | 喂给 `applyEntryPatches` 后树形符合预期 |
| `realm-emitter` | `cordis:group` + `isolate` 结构正确 | **扩展实验 3**:多插件多 realm、realm 嵌套、组外不受影响 |
| `preset-emitter` | 生成的 `agent.cordis.yml` 可被预设发现 | 真启动后 agent 看到预期工具集 |
| `scope-binder` | 链序符合声明优先级 | **扩展实验 2 的 A3**:三层以上链、rebind、dispose |
| `client-gate` | 主机行 disabled 标记正确 | 启动清单里对应前端半消失(验证 2.5 的派生链) |

### T3 · 集成 —— 真 dsh 启动

在 `dsh-lab` 里构造**真实冲突场景**,启动完整 profile:

1. **工具名撞车**:两个插件都注册 `bash` → 断言两者都活、按链序裁决、模型看到的名字未变
2. **撞官方工具**:插件注册 `bash` 撞 `dsh-tool-bash` → 断言不再抛错
3. **entry id 撞车**:两个插件都插 `storage` → 断言按包名重写后共存
4. **孤儿补丁**:插件补丁指向不存在的 id → 断言组合期报错而非静默
5. **配置行丢字段**:插件 override `system-prompt` 只写部分键 → 断言检出并报告丢失键
6. **前端 single 槽争用**:两个插件抢 `details` → 断言只有一个前端半进清单
7. **waterfall 短路**:插件在 `tools/pre-execute` 短路 → 断言哨兵检出
8. **底座策略免疫**:同上场景下 `guard()` 仍生效
9. **热重载**:重载后决策幂等重现
10. **底座自身失败**:注入故障 → 断言退化为直通而非阻断启动

### T3.5 · 前端不可避免冲突 —— 专项实验

前端 `single` 槽争用(24 组 / 303 包)底座只能二元取舍,这是**已知的能力缺口**,需要实验量化代价并为上游提案取证。

**E1 · 代价量化**:从生态里取真实的 `single` 槽争用组合(`details` 108 包、`conversation.hero.workspace.directoryFlow`、`sidebar.workspaces.directoryFlow`),两两组合启动 Web,记录:
- 不加底座:是否抛错 / 哪个渲染 / 是否稳定复现
- 加底座(二元取舍):被禁的那个插件损失了什么功能

**E2 · A/B 启动成功率**:随机抽 N 组"已知会冲突"的插件组合,对比有无底座的启动成功率与可用功能数。这是底座价值的直接证据。

**E3 · 上游改动原型(最重要)**:在 `dsh-lab` 里**本地实现 PR 3**——给 `BootPluginRow` 加 `priority`,主机侧清单生成时写入,客户端 `loader.create()` 透传到 `slots.register` 的 priority。然后验证:

- 两个插件抢同一 `single` 槽 → 按 priority 分层遮蔽,**都能装,低优先级的静默让位**
- 对比 E1 的二元取舍:功能损失从"整个插件被禁"降到"只有该槽位让位"

> E3 的价值不只是验证:**它把 PR 3 从"我觉得应该"变成"我做了,这是 diff 和测试"**。在只有 Discussions 没有 PR 渠道的情况下,可运行的原型是最强的论据。

### T3.6 · 免重启验证

已确认链路(`apps/cli/src/profile-boot.ts:275`):Web bundle 关掉模块重载 HMR,但启动器挂一个 `root: []` 的 watch-only 实例,并 `watchUserPatches` 监视 profile 与 home 的补丁文件——**"cordis.patch.yml 的编辑在每个长驻表面上都保持热的"**。前端侧 `client-hmr` 在 web-app 中启用,经 SSE 推 `{type:'graph'}`。

| 测试 | 断言 |
|---|---|
| 改写补丁层 | 配置热重载生效,**进程不重启** |
| 主机行 disable | `clientModules` 图变化 → SSE 推送 → 前端半下线 |
